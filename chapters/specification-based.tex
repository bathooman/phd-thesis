\chapter{From Specifications to Oracles: Requirement-Driven Symbolic Execution}\label{chapter:paper1}
Network protocols rely on precise specifications that describe how communicating parties should construct messages, how state is expected to evolve during an interaction, and how error conditions must be handled.
These specifications are expressed in RFC documents, where natural language is used to formulate requirements.
Many of these requirements involve relationships across multiple packets.
For example, a field in one message may depend on a value in a previous message, or a sequence must follow a specific ordering that is valid for the selected key exchange method.

Testing such requirements is challenging. 
Traditional fuzzers concentrate on triggering crashes and often operate without awareness of protocol state.
Standard symbolic execution (SE) tools are powerful for analyzing single inputs, yet they do not directly address multi-packet interactions or stateful requirements.
When applied naively to protocol implementations, these tools either fail to explore relevant paths or become overwhelmed by the path explosion caused by large input spaces.

The work presented in this chapter introduces a technique that applies SE in a requirement-driven manner.
The aim is to systematically search for inputs that violate specific RFC requirements and to produce concrete packet sequences that expose the deviation in the implementation under test.
The objective is not limited to detecting crashes. 
It also focuses on revealing non-conformance flaws that may affect security or interoperability.
\section{Technique}
\subsection{Extracting Specification Requirements}\label{sec:extract-req}
The first step is to extract protocol requirements from the RFC text and express them as logical predicates over the packets exchanged during a protocol session.
RFCs typically use particular keywords such as "MUST", "MUST NOT", "REQUIRED", "SHALL", and "SHALL NOT" to indicate the strictness of a requirement~\cite{RFC2119}.
These statements can be formulated into predicates that describe how packets must be structured and how they relate to one another.

Protocol specifications contain requirements of different kinds.
Some requirements constrain the validity of individual packets or sequences of packets, specifying conditions under which inputs must be rejected.
Other requirements relate received inputs to the outputs that an implementation is expected to generate in response, for example by constraining fields in outgoing messages based on earlier inputs in the protocol session.
In both cases, requirements often involve relationships across multiple packets and cannot be expressed as predicates over a single message in isolation.

To express such predicates precisely, we adopt a simple model of interaction.
For DTLS, a session is viewed as a finite sequence of records received by one protocol party, which we denote by $R$.
We write $r, r' \, \in \, R$ to range over individual records in the sequence.
Equality between records refers to their position in the sequence: $r = r'$ means that they are the same occurrence of a record, not merely two records with identical contents.
Each record is a structured object containing fields such as \rfc{type}, \rfc{epoch}, and \rfc{sequence\_number}.
For example, $r\rfcm{.sequence\_number}$ is used to refer to the sequence number of a record $r$.

As an example of an input-output requirement, consider the following rule from the
DTLS RFC~\cite[p.~17]{RFC6347} and its errata (ID: 5186), which concerns the handling
of message sequence numbers during cookie exchanges:
%
\rfcdisplayquote{%
In order to avoid sequence number duplication in case of multiple cookie exchanges, the server MUST use the message\_seq in the ClientHello as the message\_seq in its initial ServerHello.}%
%
Letting $\mathit{resp}(r,i)$ denote the $i$th output record generated in response to an input record $r$, this requirement can be expressed as:
%
\begin{equation}\label{const:msnsame}\normalsize
	\begin{split}
		& \scriptstyle \forall r \in R :\ r\rfcm{.msg\_type}\, =\, \rfcm{client\_hello} \implies \\[-5pt]
		& \scriptstyle \qquad\qquad (\responseto{r}{1}\rfcm{.msg\_type}\, =\, \rfcm{server\_hello} \implies \\[-5pt]
		& \scriptstyle \qquad\qquad\quad  \responseto{r}{1}\rfcm{.message\_seq}\, =\, r\rfcm{.message\_seq})
	\end{split}
\end{equation}
%
This predicate captures a dependency between an incoming record and a subsequent outgoing record and illustrates how input-output relationships specified in the RFC can be formalized.
This formulation relies on the fact that the \rfc{msg\_type} field of a record indicates the type of the enclosed (and possibly fragmented) handshake message.

A simple yet representative example of an input-validity requirement appears in the DTLS RFC~\cite[p. 13]{RFC6347}, which specifies the uniqueness of record sequence numbers within a session.
Each DTLS record contains a 48-bit \rfc{sequence\_number} field that uniquely identifies the record within a session.
This field is incremented for every record sent, usually starting from zero. 
The receiver uses sequence numbers to process records in the correct order and to detect duplicates, since any two records with the same \rfc{sequence\_number} indicate a replay.
The requirement is formulated in the RFC as follows:
%
\rfcdisplayquote{%
For each received record, the receiver MUST verify that the record contains a sequence number that does not duplicate the sequence number of any other record received during the life of this session.}%
%
This requirement serves as a protection against replayed records.
For a set of records $R$ received during a DTLS session, the requirement can be expressed in predicate logic as:
%
\begin{equation}\label{const:rsnuniqueness}\normalsize
	\forall r, r' \in R :\, r \neq r' \implies 
	r\rfcm{.sequence\_number}\, \neq\, r'\rfcm{.sequence\_number}
\end{equation}
%
This formula captures the essential rule that no two records may share the same sequence number.
We will use this requirement as a running example in the remainder of this chapter
to illustrate how formalized requirements are tested using SE.

A further example of an input-validity requirement that relates multiple records concerns the DTLS epoch field.
The epoch identifies which set of session keys were used to protect a record, and the RFC specifies that its value should be initialized with zero and increase exactly when a \emph{ChangeCipherSpec} is received~\cite[p. 8]{RFC6347}.
Let $r_i$ denote the $i$th record in the sequence.
For $n$ received records in a DTLS session, we capture this requirement with the following formula:
\begin{equation*}\label{const:epoch}
	\begin{split}
		& \scriptstyle \forall i \in \mathbb{N}, 2 \leq i \leq n: \\[-5pt]  %% \forall r_i \in R:
		& \scriptstyle \quad (r_1.\rfcm{epoch}\, =\, 0)\ \wedge \\[-5pt]
		& \scriptstyle \quad (\mathtt{if}\ r_{i-1}.\rfcm{type}\ =\, \rfcm{change\_cipher\_spec}\
		\mathtt{then}\ r_i.\rfcm{epoch}\ =\, r_{i-1}.\rfcm{epoch} + 1\\[-5pt]
		& \scriptstyle \quad\ \mathtt{else}\ r_i.\rfcm{epoch}\, =\, r_{i-1}.\rfcm{epoch})
	\end{split}
\end{equation*}
This formula specifies that the \rfc{epoch} of the first record is zero, and that for all subsequent records the value of the \rfc{epoch} field is either one greater than that of the previous record or equal to it, depending on whether the \rfc{type} field of the previous record is \rfc{change\_cipher\_spec}.

Once formulated, these predicates can be used to restrict SE to those parts of the input space where a violation of the requirement may occur.

Although the logical predicates are not executed directly, formulating the requirements in this way is still essential.
RFC text is written in natural language and often describes relationships across multiple packets, message types, or stages of a handshake.
Writing these requirements as predicates makes their meaning precise and exposes exactly which fields participate in them.
This precision is necessary because SE must focus on the fields that matter for the requirement and explore the conditions under which the requirement may be violated.
In short, the logical formulation defines the requirement in a clear and unambiguous way, and this definition is what guides the later testing steps.

\subsection{Symbolic Execution}
Symbolic execution is applied to each tested implementation through a dedicated test harness that replays a pre-captured sequence of records from a valid DTLS handshake and passes them one at a time to the implementation under test.
Each record is parsed into a structured representation, which enables SE to access and manipulate selected fields. 
The harness provides a deterministic environment by controlling the order of record processing and by removing nondeterministic behavior such as cookie verification or timeouts.

Symbolic execution requires the implementation under test to behave in a fully deterministic manner.
Any nondeterministic behavior such as random number generation, retransmissions, or time-based actions would cause the symbolic executor to branch unnecessarily or to follow paths that differ from those observed during record capture.
For this reason, the harness must execute deterministically so that the same control flow is obtained both when capturing the handshake and when symbolically executing it.
A deterministic setup ensures that any variation observed by SE arises solely from symbolic fields.
Pre-captured records are used for the same reason.
A full DTLS handshake contains many fields that are irrelevant for a given requirement, and making entire records symbolic would cause path explosion.
By replaying a fixed valid sequence and making symbolic only the fields involved in the requirement, we restrict SE to the part of the input space where a violation may occur.
Parsing records into structured representations further supports this goal by allowing the analysis to target individual protocol fields rather than byte arrays.

The requirements introduced in the previous section fall into two classes.
The first class consists of input-validity requirements, which specify conditions that each received record must satisfy. 
These requirements describe how the implementation should reject malformed inputs. 
When checking an input-validity requirement, SE makes the relevant fields symbolic and introduces assumptions that correspond to the negation of the requirement.
This directs the analysis toward inputs under which the requirement may be violated, and an assertion is used to detect if the implementation processes such invalid inputs in a forbidden way. 
The second class consists of input-output requirements. 
These requirements describe how an implementation must respond to valid inputs, for example by producing an output message whose fields satisfy a specified relation. 
For these requirements, SE assumes that the input is valid and places the requirement itself in an assertion that checks the correctness of the generated output.

For input-validity requirements, SE should concentrate on requirement-violating inputs rather than on the vast space of valid inputs, so the harness introduces assumptions that encode the negation of the requirement.
These assumptions restrict SE to inputs under which the requirement may be violated.
The final step is to check whether the implementation uses the invalid input in a forbidden way.
Protocols differ in how malformed inputs must be handled.
Some specifications require discarding the input, others mandate generating an alert, and others require immediate termination of the connection.
In DTLS, the general rule~\cite[p. 14]{RFC6347} for handling invalid records requires discarding them and states that implementations may generate a fatal-level alert message.
For DTLS, we therefore approximate forbidden behavior by checking whether the handshake nonetheless progresses.
A failing assertion is inserted at the point where the implementation reaches the code that completes the handshake.
If SE reaches this point, it means that the implementation advanced through the handshake despite the invalid input, which indicates a violation of the requirement.

The predicate in \Cref{const:rsnuniqueness} formulates an input-validity requirement that states that no two records in a session share the same sequence number.
To apply our technique to evaluate this requirement for a server, the harness loads the sequence of pre-captured records that a DTLS server would receive during its handshake and marks the client-side \rfc{sequence\_number} fields as symbolic.
All other fields remain concrete.

An assume statement is then introduced that indicates that at least two symbolic sequence numbers are equal.
This directs SE to explore precisely those assignments that violate uniqueness.
To evaluate the effect of this invalid input, a failing assertion (\eg \texttt{assert(false)}) is placed at the code location that indicates successful completion of the handshake. 
If SE reaches this assertion, it means that the implementation completed the handshake even though it received a record with a duplicate sequence number. 
The assertion then fails, and the SE engine reports the concrete assignments that triggered this behavior.

In our implementation, handshake completion is detected by instrumenting the code at the point where the implementation expects to receive and process the \emph{Finished} message. 
This point marks the transition into the encrypted phase of DTLS and therefore indicates that the handshake has completed successfully. 
A failing assertion is inserted at this location. 
If SE reaches this assertion, it means that the implementation progressed through the handshake despite having received an invalid input earlier in the sequence. 
This provides a uniform and lightweight method for detecting forbidden progress across different DTLS implementations without requiring detailed inspection of their internal state machines.
\subsection{Test Case Construction and Validation}
When SE discovers a violating execution path, the engine provides concrete values for all symbolic fields involved.
To construct a test case, these values are substituted back into the structured record representations used by the test harness, while all other fields retain their original concrete values from the pre-captured handshake.
The resulting records are then serialized into byte arrays that follow the exact wire format of the protocol.

For the sequence number requirement, this means that SE produces a concrete assignment in which two records share the same sequence number. 
These values replace the symbolic fields in the corresponding records, creating a concrete record sequence that instantiates the violation of the predicate in \Cref{const:rsnuniqueness}.

These concrete record sequences are replayed against the unmodified implementation outside the SE environment.
Validation is done by observing whether the unmodified implementation accepts the sequence and completes the handshake.
Since handshake completion is used as an approximation for protocol progress, a successful handshake in the presence of an invalid record constitutes a confirmed violation of the corresponding requirement.
In the sequence number example, if the server completes its handshake despite the duplicate sequence number, the requirement is violated and the test case is confirmed.

\section{Evaluation}
The technique was applied to four implementations of the DTLS protocol. These included OpenSSL, MbedTLS, and two variants of TinyDTLS. 
A collection of sixteen requirements from the DTLS RFC~\cite{RFC6347} were formulated and tested. These requirements ranged from record layer constraints, concerning content type, version fields, and epoch handling, to handshake layer rules related to message ordering, fragmentation, and message sequence numbers.

The evaluation revealed a total of \emph{thirty six} unique bugs, seven of which were classified as vulnerabilities. Several issues were memory related, including out of bounds accesses during message reassembly. Others concerned logical violations of the specification, such as incorrect validation of version fields, improper handling of repeated handshake messages, and failures to respect message ordering rules. Many issues were identified within a short symbolic exploration time, and all of them were acknowledged and fixed by the developers.

In addition to uncovering new issues, our technique also reproduced a previously known exploitable vulnerability in OpenSSL's function for reassembling fragmented messages.
This reproduction confirms the power and promise of our technique.

For a detailed description of the technique's implementation, the full set of input-validity and input-output requirements we evaluated, and a comprehensive analysis of the issues we discovered, the reader is referred to Paper \URoman{1}.

\section{Limitations}\label{sec:paper1-limitations}
The technique presented in this chapter has two main limitations that motivate the next contribution of this thesis.
The first limitation is that the code responsible for checking requirements must be directly inserted into the source code of the implementation under test.
This involves adding calls to a shared library at specific locations in the implementation.
Since these locations differ between implementations and between versions, the process requires a detailed understanding of the code base and must be repeated whenever the implementation changes.
This reduces the portability of the technique and increases the manual effort required to apply it.

The second limitation concerns the reliance on completing a protocol interaction.
In the case of DTLS, this means that SE must reach either the successful completion of the handshake or a definite failure triggered by the invalid input.
As a result, SE may be forced to explore many paths that lie far beyond the part of the execution that is relevant to the requirement being tested.
This unnecessarily increases the symbolic search space and can significantly slow down the detection of violating inputs.

These two limitations motivate the need for a technique that avoids instrumentation of the implementation and that can detect requirement violations without relying on the completion of a full protocol exchange.
The next chapter introduces a monitor-based approach that addresses both issues by moving requirement checking outside the implementation and by enabling earlier detection of violation points.

\chapter{Background}\label{chapter:background}
\section{Traditional Testing Methods}
Testing has long been a central technique for assessing software correctness.
Traditional approaches operate by exercising selected program behaviors under representative inputs and observing whether the outputs match the expectations defined by the relevant specification.
In practice, this usually involves a hierarchy of testing activities.
Unit tests target individual functions or modules in isolation, while integration and system tests examine interactions among components and validate end-to-end functionality in realistic settings.
Regression tests ensure that previously correct behavior is preserved as the software evolves.

These techniques remain highly useful, yet their effectiveness is inherently limited by the scope of the selected test cases.
Most software systems have large input spaces and complex control flow, so manually designed test suites typically cover only a fraction of the possible behaviors.
Corner cases and rarely exercised paths often remain untested, allowing subtle flaws to stay undetected.

Even with modern advances, testing remains inherently incomplete, as test cases, whether constructed manually or generated automatically, explore only a subset of the behaviors a program may exhibit in practice.
Testing can therefore increase confidence in correctness by revealing flaws in the observed executions, but it cannot guarantee their absence in real-world software systems.

While this fundamental limitation applies to all testing techniques, traditional approaches face additional practical constraints.
Manually crafted tests scale poorly to complex systems, provide limited coverage of hard-to-reach behaviors, and require substantial effort to maintain as software evolves.
These practical challenges motivated the development of more systematic and automated testing approaches, particularly in domains where correctness depends on structured inputs, ordered sequences of operations, or adherence to detailed specifications.

The next subsection introduces such automated methods in the context of protocol testing.

\section{Modern Automated Approaches for Protocol Testing}
As software systems grew in complexity, testing practices increasingly incorporated automation to improve coverage and reduce reliance on manually crafted test suites.
Automated techniques aim to explore program behavior more systematically, exercise hard-to-reach code paths, and reduce the effort required to maintain large test suites as software evolves.
These goals are particularly relevant for protocol implementations, where correctness depends on structured message formats, precise constraints on message order, and stateful interactions.

A widely adopted automated technique is \emph{Model-Based Testing}~\cite{MBT-reactive@2005, Utting:mbt@2006}, which derives test cases from an abstract behavioral model such as a finite-state machine.
When sufficiently accurate models are available, this approach provides a systematic way to explore a broad range of message sequences and protocol states.
Each generated sequence represents a potential interaction between protocol entities, and the observed behavior of the implementation is compared against the model's expected behavior to assess conformance.
However, constructing accurate models from natural-language specifications is labor-intensive, and inaccuracies can directly affect the resulting tests. 

\emph{Fuzz testing} offers a complementary strategy based on automatically generating large numbers of inputs, often by mutating valid messages or message sequences. 
Coverage-guided fuzzers~\cite{AFL, AFLplusplus-Woot20} prioritize inputs that trigger previously unexplored control-flow branches and have proven effective at exposing robustness issues such as crashes and memory-safety violations. 
Traditional fuzzers treat each input largely in isolation, which makes them less effective for exploring deeper protocol behaviors that depend on long-lived internal state or structured message flows. 
Recent state-aware fuzzers~\cite{AFLNET@ICST-20, SnapFuzz@ISSTA-22} mitigate this limitation by incorporating message types and simple feedback on server responsiveness, enabling more targeted exploration of protocol state. 
However, their notion of state remains coarse-grained and heuristic, and they cannot direct the fuzzer toward exercising or violating specific semantic rules defined in the protocol specification, which reduces their utility for conformance testing.

\emph{Differential testing}~\cite{McKeeman@DiffTesting, RFCcert@ICSE-18, SymCerts, PKCS} provides another automated technique suitable for protocols. 
By exercising multiple independent implementations with the same inputs and comparing their outputs, it can reveal behavioral differences in how implementations process those inputs. 
The inputs may vary not only in the sequence of messages but also in the specific values carried by individual fields, either of which can drive implementations into different behaviors. 
Such differences do not automatically indicate flaws, since protocol specifications often allow multiple conforming responses. 
The specification should therefore be consulted to determine whether a discrepancy is permitted or whether one implementation violates the expected behavior. 
The effectiveness of differential testing depends heavily on the richness of the test suite, because discrepancies can only be observed for the interactions that are actually exercised. 
Although differential testing avoids the need for an explicit behavioral model, it relies on the availability of multiple mature implementations.

Several other automated techniques have also been explored in the domain of protocol testing.
Grammar-based input generation~\cite{Peach@2004, SPIKE@2002} constructs syntactically valid messages from protocol grammars, allowing systematic exploration of field combinations, encodings, and optional structures that mutation-based fuzzing may miss.
Model learning techniques~\cite{FH2017, FJV2016, SSH@SPIN-2017} infer an implementation's state machine from observed interactions and use the inferred model for targeted test generation or conformance checks.
State fuzzing techniques~\cite{MessyTLS@CACM-2017, ruiter2015, DTLS@USENIX-20, DTLS-Fuzzer@ICST-22} combine inferred state models with fuzzing to guide mutations toward specific protocol states or transitions, enabling the exploration of behaviors that depend on multi-step interactions rather than isolated messages. 
Together, these approaches extend the behaviors that automated testing can exercise and complement model-based and mutation-based techniques.

Despite these advances, automated approaches still struggle to exercise certain behaviors, especially when those behaviors depend on specific branching choices or arise only under narrowly constrained conditions.
Because input generation alone cannot always guide execution toward these areas, it is often useful to complement such techniques with approaches that reason directly about program logic.
The next section introduces symbolic execution, which executes programs with symbolic inputs to explore feasible execution paths.

\section{Symbolic Execution}
Symbolic execution (SE)~\cite{King@CACM-76} is a white-box technique that analyzes programs in which some inputs or variables are designated as symbolic, and explores all code paths that are feasible for some assignments to these symbolic variables, thereby reasoning over the entire space of their possible values.
During symbolic execution, the SE engine maintains two key structures for each explored path: a symbolic store ($\mathtt{\sigma}$), which maps program variables to symbolic expressions representing their current values, and a path condition ($\mathit{PC}$), which accumulates the logical constraints that must hold along the path being explored.

In practice, SE engines such as KLEE~\cite{KLEE@OSDI-08} operate incrementally. 
As the program executes, each instruction is evaluated while tracking how its result depends on symbolic inputs: assignments update the symbolic store, memory loads retrieve the current symbolic expression of the addressed location, and conditional branches may fork execution when their predicates involve symbolic data.
At each branch, the engine conjoins the branch predicate with the current path condition and consults an SMT solver to determine whether the branch is feasible.
Infeasible branches are pruned immediately, while feasible ones continue with their updated symbolic state.

To illustrate, consider the simple C function in \Cref{lst:max-func}, which is intended to return the larger of two integers provided as input.
Although the function successfully compiles and may appear correct, it contains a subtle flaw: when $\mathtt{a}$ equals $\mathtt{b}$, the variable $\mathtt{result}$ is returned without being initialized. 
Reading an uninitialized variable in C constitutes \emph{undefined behavior}, which yields arbitrary values or may cause a crash depending on memory state.
This type of flaw is common in real-world systems and is notoriously difficult to detect through conventional testing.
\smallskip
\begin{listing}[ht]
	\centering
	\begin{minipage}{0.75\linewidth}
		\begin{minted}[linenos, autogobble]{C}
			int max(int a, int b) {
			  int result;
			  if (a > b)
			    result = a;
			  else if (a < b)
			    result = b;
			  // Missing assignment when a == b
			  return result;
			}
		\end{minted}
	\end{minipage}
	\caption{Function returning the maximum of two integers.}
	\label{lst:max-func}
\end{listing}
\smallskip

Symbolic execution begins by initializing symbolic values $\mathtt{a_0}$ and $\mathtt{b_0}$. 
The initial symbolic state is:
\[
\begin{aligned}
	\sigma_0 &= \{ a \mapsto a_0,\, b \mapsto b_0 \},\\
	PC_0 &= \text{true}.
\end{aligned}
\]
The conditional statements in \Cref{lst:max-func} yield three feasible execution paths.
When $a_0 > b_0$, corresponding to the if branch on line 3, the program returns $\mathtt{a}$ (Path 1).
When $a_0 < b_0$, corresponding to the else if branch on line 5, it returns $\mathtt{b}$ (Path 2).
Finally, when $a_0 = b_0$, execution skips both assignments, returning an uninitialized $\mathtt{result}$ (Path 3).

\setlength{\jot}{0.3em}
\[
\begin{aligned}
	\textsc{Path 1:}\quad &PC_1 = (a_0 > b_0) &&\Rightarrow \text{return } a_0,\\
	\textsc{Path 2:}\quad &PC_{2} = (a_0 < b_0) &&\Rightarrow \text{return } b_0,\\
	\textsc{Path 3:}\quad &PC_{3} = (a_0 = b_0) &&\Rightarrow \text{uninitialized read of } \texttt{result.}
\end{aligned}
\]

For compactness, the symbolic state corresponding to the faulty path can be summarized as:
\begin{tcolorbox}[
	title=Symbolic state on Path 3,
	colback=gray!3,
	colframe=blue!40!black,
	boxrule=0.3pt,
	left=4pt, right=4pt, top=2pt, bottom=1pt,
	sharp corners
	]
	$$
	\begin{aligned}
		\sigma_{3} &= \{ a \mapsto a_0,\, b \mapsto b_0,\, \texttt{result} \mapsto \bot \},\\
		PC_{3} &= (a_0 = b_0).
	\end{aligned}
	$$
	\vspace{1pt}
\end{tcolorbox}

When KLEE explores Path 3, the variable $\mathtt{result}$ has no prior assignment in the symbolic state.
When execution reaches the $\texttt{return result}$ statement, the engine evaluates a load from the symbolic memory.
Because $\mathtt{result}$ has no defined symbolic value, this load produces an \emph{uninitialized read}, which KLEE reports immediately.

Although the solver is consulted incrementally at each branch to determine feasibility, KLEE also invokes the solver at the end of each feasible path to construct a concrete assignment (a witness) that satisfies that path condition.

Finally, executing the program with the concrete values $(a,b)=(4,4)$, the witness for Path 3 reveals the flaw: an uninitialized read of \texttt{result}. 
Symbolic execution engines typically report such behavior as an uninitialized variable read accompanied by a counterexample witness. 
The boxed state above clearly exposes the root cause: the symbolic store records $\texttt{result}\mapsto\bot$ (undefined) while the path condition $\mathit{PC}_{3}$ remains satisfiable.

Beyond this small example, SE provides several advantages as a testing technique.
Its systematic exploration of feasible execution paths, combined with the use of SMT solvers to reason about constraints over symbolic variables, enables it to uncover subtle errors that are difficult to expose through conventional testing.
The witnesses produced by the solver allow precise and reproducible test cases, and assertions or specification rules can be embedded directly into the tested program to serve as correctness oracles.

Several mature SE engines have demonstrated the practical value of the technique.
KLEE~\cite{KLEE@OSDI-08} has been widely used to analyze system libraries and embedded utilities, achieving high coverage and uncovering numerous real-world bugs. 
S2E~\cite{S2E@12} extends SE to full-system environments, allowing analysis of complex binaries that interact with operating systems services and hardware abstractions.

Despite its strengths, SE also faces several well-known limitations.

\textbf{Path explosion.} The number of feasible execution paths in a program typically grows exponentially with the number of branches, a common phenomenon known as the path-explosion problem.

\textbf{Constraint complexity.} Constraint solving becomes increasingly expensive when programs manipulate pointer-heavy data structures, arrays with symbolic indices, or arithmetic expressions whose satisfiability requires nonlinear reasoning.

\textbf{Environment modeling.} Real-world programs interact with their environment through file systems, network sockets, timers, and other operating-system services. 
Because symbolic execution is a white-box technique, it can only reason about behavior that is executed inside the symbolic interpreter. 
External services operate outside this scope and return concrete data such as file contents, incoming packets, or timer values that the engine cannot control or fork. 
For example, a network read depends on the exact bytes delivered by the OS, which cannot be treated symbolically without replacing the socket interface with a model that produces symbolic data. 
Some SE engines~\cite{KLEE@OSDI-08} therefore fall back on \emph{concretization}, supplying fixed concrete values for such interactions when no model is available. 
While this allows execution to proceed, concretization restricts exploration to a single concrete behavior and may cause the engine to miss feasible paths that depend on alternative inputs. 
Symbolic models avoid this loss of coverage but are difficult to implement comprehensively and can significantly affect scalability.

Taken together, these challenges are amplified in the context of network protocol implementations.
Reaching specific protocol states often requires carefully orchestrated sequences of inputs, some of which depend on subtle constraints encoded in the specification.
Classical SE provides no mechanism to guide execution toward such message sequences, to represent protocol-level state transitions, or to validate conformance rules that are not directly reflected in the control flow of the implementation.
Addressing these limitations requires extending SE with ways to control incoming protocol messages, to represent protocol state transitions, and to relate program paths to behaviors described in the specification.
These extensions form the basis of the techniques developed in the remainder of this thesis.
